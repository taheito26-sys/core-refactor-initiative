# Push Notifications

Raseed delivers push notifications through one server function, `push-send`,
for the browser/PWA (Web Push), Android (FCM), and iOS (APNs).

## Architecture

```
INSERT INTO public.notifications
        │
        ▼
trg_notifications_dispatch_push            (AFTER INSERT trigger)
        │  pg_net, asynchronous, carries the private x-push-secret
        ▼
supabase/functions/push-send
        ├── loads the notification, builds the deep-link path
        ├── checks master switch, category preference, quiet hours
        ├── loads this user's endpoints
        │     ├── web_push_subscriptions  → Web Push (VAPID)
        │     └── push_device_tokens      → FCM v1 (Android)
        │                                  → APNs (iOS, 64-hex token)
        └── removes endpoints the provider reports as gone (404/410/UNREGISTERED)
```

The trigger never blocks a notification insert: any dispatch error is caught and
logged as a warning, and the notification is saved regardless.

below.

## Database objects

| Object | Purpose |
| --- | --- |
| `push_device_tokens` | FCM/APNs tokens, one row per physical device |
| `web_push_subscriptions` | Browser push endpoints (`endpoint`, `p256dh`, `auth`) |
| `notification_settings` | Account-wide push switch, quiet hours, timezone |
| `notification_reminders` | Due reminders used by the `notification-reminders` cron |
| `push_dispatch_config` | Private shared secret and auto-generated VAPID key pair |
| `register_push_token` / `unregister_push_token` | Move a device token to the signed-in account |
| `register_web_push_subscription` / `unregister_web_push_subscription` | Same for browser endpoints |
| `set_notification_presence` | Marks this device as actively viewing the app |

`push_dispatch_config` has RLS enabled with no policies and is revoked from
`anon`/`authenticated`; only the service role (the edge function) and the
`SECURITY DEFINER` trigger can read it.

## Preferences

* **Account-wide switch** — `notification_settings.push_enabled`. Pauses delivery
  to every device without unsubscribing them.
* **Per-category** — `notification_preferences.push_enabled`. The push-send
  function reads it for the notification's category.
* **Quiet hours** — `notification_settings.dnd_enabled/dnd_start/dnd_end/timezone`.
  Evaluated in the user's timezone, including overnight windows.
* **Foreground suppression** — each subscription/token stores `active_until`.
  While a browser is visible it heartbeats every 45 seconds; the server skips an
  OS notification for that device because the in-app alert is already showing.
  Calls and test notifications bypass this.
* **In-app and sound toggles** — enforced client-side by `useNotifications`
  (`in_app_enabled`, `sound_enabled`) and mirrored to localStorage for the Web
  Audio chimes.

## Client flow

1. `usePushRegistration` (native only) asks for permission, registers with FCM,
   and saves the token through `register_push_token`.
2. `useWebPushRegistration` (web only) silently refreshes an existing browser
   subscription after sign-in. It never prompts.
3. The settings card (`PushNotificationsCard`, rendered by
   `NotificationPreferencesPanel`) is the explicit user gesture that calls
   `Notification.requestPermission()` and creates the subscription.
4. `public/push-sw.js` is imported by the generated Workbox service worker. It
   shows the notification, updates the app badge, and routes notification clicks
   to the deep link embedded by push-send.
5. On sign-out, `unregisterPushDevicesOnSignOut` deletes this device's endpoints
   while the session is still valid. Explicitly turning push off sets a local
   opt-out flag so the app does not silently re-register on the next launch.

## Setup

### Web Push (no external account required)

The VAPID key pair is generated by `push-send` on first use and stored in
`push_dispatch_config`; no private key is committed. Web Push works in Chrome,
Edge, Firefox, and Safari 16.4+ (on iOS the PWA must be installed to the Home
Screen first).

### Native Android (FCM)

1. Create a Firebase project and add an Android app with package
   `com.taheito26sys.corerefactorinitiative`.
2. Download `google-services.json` into `android/app/`. The Gradle build only
   applies the Google Services plugin when that file exists.
3. In Google Cloud, enable the **Firebase Cloud Messaging API (V1)**.
4. In Firebase **Project settings → Service accounts**, generate a new private
   key (Firebase Admin SDK). Store the JSON in the Supabase edge-function secret
   `FCM_SERVICE_ACCOUNT_JSON`.
5. Rebuild and sync: `npm run build && npx cap sync android`.

Without step 4 the function still delivers Web Push and reports
`fcm_configured: false`; Android devices are skipped.

### Native iOS (APNs)

The Capacitor Push Notifications plugin returns the raw APNs device token on
iOS. `push-send` sends those 64-character tokens directly to APNs; a Firebase
service account is not used on this path.

1. In Apple Developer **Certificates, Identifiers & Profiles → Keys**, create a
   key with **Apple Push Notifications service (APNs)** enabled. Download the
   `.p8` once and note its **Key ID**. Note the **Team ID** from Membership.
2. In Xcode, select the **App** target → **Signing & Capabilities** → add
   **Push Notifications**. Under **Background Modes**, enable
   **Remote notifications** (already declared in `Info.plist`).
3. Set these Supabase secrets:
   * `APNS_KEY_ID` — the Key ID
   * `APNS_TEAM_ID` — the Apple Team ID
   * `APNS_PRIVATE_KEY` — the complete `.p8` contents, including the BEGIN/END lines
   * `APNS_BUNDLE_ID` — optional; defaults to
     `com.taheito26sys.corerefactorinitiative`
   * `APNS_USE_SANDBOX` — `true` for Xcode/debug builds, `false` for
     TestFlight/App Store builds
4. Rebuild and sync: `npm run build && npx cap sync ios`, then run on a physical
   iPhone. The iOS simulator does not receive real APNs pushes.

`GoogleService-Info.plist` is not required for the APNs path. If you later add
the Firebase iOS SDK (or `@capacitor-firebase/messaging`) to obtain an FCM
token instead, the same `FCM_SERVICE_ACCOUNT_JSON` can deliver to iOS as well;
`push-send` recognizes non-hex iOS tokens as FCM tokens.

## Testing

1. Open **Settings → Push Notifications**.
2. Click **Enable notifications** and accept the browser prompt.
3. Click **Send test notification**; the toast reports how many browser and
   native endpoints received it.
4. Close the tab and insert a notification for the account. The OS notification
   should appear and clicking it should open the target page.
5. For native, run the app on a physical device and use the same test button.
   Android needs `google-services.json` + `FCM_SERVICE_ACCOUNT_JSON`; iOS needs
   the Push Notifications capability + `APNS_*` secrets.

Useful SQL checks:

```sql
SELECT count(*) FROM push_device_tokens WHERE user_id = '<uuid>';
SELECT platform, left(token, 12), updated_at FROM push_device_tokens WHERE user_id = '<uuid>';
SELECT count(*) FROM web_push_subscriptions WHERE user_id = '<uuid>';
SELECT * FROM notification_settings WHERE user_id = '<uuid>';
SELECT * FROM push_dispatch_config WHERE id = true; -- service role only
```

## Security notes

* `push-send` accepts an internal payload only with the `x-push-secret` header.
  A signed-in user can call only `test` (their own devices) or `call` (members of
  a room they belong to). It cannot push arbitrary content to another account.
* FCM JWTs use base64url encoding for header, payload, and signature as required
  by Google's OAuth2 token endpoint.
* APNs provider JWTs use ES256 with the `.p8` key; they are cached for 50
  minutes and never exposed to the client.
* The old `notification-reminders` direct call used the service-role key as a
  user JWT, which `auth.getUser()` rejects; reminders now rely on the same
  insert trigger as every other notification.
